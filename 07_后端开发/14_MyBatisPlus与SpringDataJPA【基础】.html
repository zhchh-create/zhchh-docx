MyBatis-Plus 与 Spring Data JPA

基础 定位：给原生 MyBatis/JPA 套一层"零 SQL 单表 CRUD"的便捷封装

本人 业务系统、数据编排平台后端用的是原生 MyBatis（写 XML/注解 SQL、动态 SQL、分页）。原生 MyBatis 灵活、SQL 可控，但"按 id 查一条、按条件列表、插一条"这种重复劳动每次都要写。MyBatis-Plus 在 MyBatis 之上加一层"继承一个接口就自带 CRUD"；Spring Data JPA 则是另一套路线——以对象模型为准、几乎不写 SQL。本页讲清这两类便捷 ORM 与原生 MyBatis 的关系和选型，诚实说明本人项目仍以原生 MyBatis 为主。

1技术点概览

一句话定位：两者都是"少写重复 SQL"——MyBatis-Plus 增强 MyBatis（复杂 SQL 仍自己写），JPA 用对象模型全自动生成 SQL。

  • MyBatis-Plus（MP）：国产，MyBatis 的增强而非替代；单表 CRUD 零 SQL，复杂查询仍写原生 SQL/XML。
  • Spring Data JPA：JPA（Hibernate 实现）的 Spring 封装；按方法名推导 SQL、以对象为中心，复杂查询用 JPQL/Example。
  • 要点本人现状：数据编排平台/业务系统 用原生 MyBatis；MP 与 JPA 均为选型对比与学习，未在生产替换。
维度原生 MyBatis（当前）MyBatis-PlusSpring Data JPA
SQL 控制权全手写，完全可控单表零 SQL，复杂仍手写框架生成，可控性弱
学习成本需写 XML/动态 SQL低，会 MyBatis 即上手较高，对象映射/缓存模型
复杂查询灵活，多表 join 自由Wrapper 条件构造 + 自定义 SQL方法名推导，复杂易翻车
适合报表/多表/性能敏感CRUD 为主的业务系统领域模型驱动、表结构稳定

2核心概念

2.1 Mapper 接口继承 BaseMapper（MyBatis-Plus）

一句话定位：你的 Mapper 接口继承 BaseMapper<实体>，就自动拥有 insert/deleteById/selectById/updateById 等单表方法，无需写 SQL。

  • 与原生 MyBatis 关系：MP 启动时为 BaseMapper 的方法自动注入 SQL，你原来的 XML/注解 SQL 照常生效。

2.2 条件构造器 Wrapper

一句话定位：用链式 API 拼 where 条件，替代写动态 SQL 的 if 标签。

  • 例：new QueryWrapper<Req>().eq("status",1).like("title","评审") 等价于一段动态 where（注意要先写构造括号 new QueryWrapper<Req>() 再链式调用；更推荐 LambdaQueryWrapper 用方法引用 .eq(Req::getStatus, 1)，列名重构不翻车、避免字符串拼错）。

图 2 Wrapper 链式条件构造（示意）

2.3 Repository 接口与方法名推导（JPA）

一句话定位：继承 JpaRepository<实体, 主键>，只需声明 findByTitleAndStatus，框架按方法名自动生成对应 SQL。

  • 命名规则：findByXxxAndYxx 会被解析成 where xxx=? and yyy=?，拼错方法名启动才报错。

2.4 实体映射注解

一句话定位：用 @TableName/@TableId（MP）或 @Entity/@Id（JPA）把 Java 对象映射到数据库表与列。

  • 共同：表名、主键、字段名靠注解映射，驼峰转下划线。

选型一句话：国内业务系统、想保留 SQL 控制力 → MyBatis-Plus；领域模型驱动、表结构稳定 → JPA；报表/多表重 join → 原生 MyBatis。

3工作原理与流程

3.1 "零 SQL CRUD"是怎么来的

一句话定位：框架在启动时扫描实体类，按表名/字段名预生成单表 SQL，运行时直接调用——省去手写重复 SQL。

4核心语法与 API 要点

4.1 MyBatis-Plus：接口即 CRUD

// 实体
@TableName("t_requirement")
public class Req {
    @TableId(type = IdType.AUTO)
    private Long id;
    private String title;
    private Integer status;
}
// Mapper 继承即拥有单表 CRUD
public interface ReqMapper extends BaseMapper<Req> { }

// Service 里直接用，零 XML
reqMapper.selectById(1L);
reqMapper.insert(req);
// 条件构造器替代动态 SQL
List<Req> list = reqMapper.selectList(
    new QueryWrapper<Req>.eq("status", 1).like("title", "评审"));

4.2 Spring Data JPA：方法名推导

public interface ReqRepository extends JpaRepository<Req, Long> {
    // 方法名自动推导成 where title=? and status=?
    List<Req> findByTitleAndStatus(String title, Integer status);
}
经验：MP 与原生 MyBatis 可无缝混用——BaseMapper 管单表，复杂报表查询仍写 XML SQL，这也是它比 JPA 在国内更流行的原因。

5实战项目经验（实战落地）

1 项目背景

一句话定位：业务系统 与数据编排平台持久层用原生 MyBatis；本节基于真实 MyBatis 实践，做 MyBatis-Plus / JPA 的选型对比。

  • 业务量级：大量单表 CRUD + 部分复杂多表/动态 SQL。

2 我的角色与职责

  • 分工：写原生 MyBatis Mapper/XML；评估新模块是否改用 MyBatis-Plus 减少样板。

3 技术栈

  • 现状：SpringBoot 3 + MyBatis；对比对象：MyBatis-Plus（增强 MyBatis）、Spring Data JPA（全自动）。

4 落地设计

  • 结论：复杂多表/报表留原生 MyBatis；标准单表 CRUD 若量大，MyBatis-Plus 可零 SQL，且与原生无缝混用。
  • 不选 JPA 的理由：项目复杂动态 SQL 多，不能放弃 SQL 控制力。

5 关键实现要点

6 真实问题与解法

  • 坑MP 与 XML 方法 id 冲突：同名方法启动报错——命名避让。
  • 要点分页插件要注册：MP 分页需注册 MybatisPlusInterceptor 并加 PaginationInnerInterceptor 才生效，用法为 selectPage(new Page<>(page, size), wrapper)。

7 量化成果

  • 评估可省去约六成单表 CRUD 的样板 XML（估算）；判定现有稳定系统不推翻，作为新模块默认选择。

8 协作与排期过程

  • 选型结论与后端团队达成一致：保持原生 MyBatis，新模块按团队约定再决定是否引入 MP。

9 复盘与可复用经验

  • 便捷 ORM 只接管单表：复杂 SQL 永远保留手写。
  • 选型看 SQL 控制力需求。

10 面试讲法

"业务系统/数据编排平台用原生 MyBatis，我做过 MP 与 JPA 的选型：保留复杂 SQL 控制力，单表 CRUD 才交给 MP，不盲目全自动。"

6易错点与面试重点

6.1 JPA 方法名拼错

一句话定位：findByTitl（少个 e）编译不报错，启动时才解析失败。

  • 正解：严格按命名规则写，复杂查询直接写 @Query JPQL，别堆超长方法名。

6.2 便捷 ORM 写出 N+1 查询

一句话定位：查列表时逐条查关联对象，100 条数据发 101 次 SQL。

  • 正解：用 join fetch / 批量抓取，N+1 是 JPA 最经典的性能坑。

图 3 N+1 查询问题（示意）

6.3 以为 MP 能替代手写 SQL

一句话定位：多表 join、报表聚合硬套 Wrapper，越写越难维护。

  • 正解：复杂查询老老实实写 XML/注解 SQL，MP 只接管单表。

6.4 忽略逻辑删除字段配置

一句话定位：MP 的逻辑删除要配全局字段，否则 deleteById 真把行删了。

  • 正解：配置 logic-delete-field，删除自动转成 update set deleted=1。
