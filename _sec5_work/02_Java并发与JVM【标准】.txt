  <h2><span class="num">5</span>使用案例（真实项目落地）</h2>
  <h3>案例：电力大屏分布式数据聚合——线程池并行 + JVM 容器内调优</h3>
  <p><strong>业务场景</strong>：电力大屏可视化项目群（iClean 智能监控，Vue2 + Java，含分布式数据聚合）的一个大屏首屏要同时聚合多个后端微服务的实时数据（负荷、告警热力、设备树、统计 KPI）。初版串行调用，首屏转圈 700ms+，值班反馈"打开大屏要等半天"。同时服务跑在容器里，偶发 Full GC 导致大屏刷新卡住几秒。</p>
  <p><strong>落地步骤</strong>：</p>
  <ol>
    <li>把串行的多次远程调用改为提交到同一个业务线程池，用 <code>CompletableFuture</code> 并行，<code>allOf</code> 等全部完成后汇总。</li>
    <li>线程池用有界队列 + CallerRunsPolicy，拒绝时退回 Tomcat 工作线程自己跑，形成自然反压，而不是无限排队 OOM。</li>
    <li>每路远程调用都加超时（orTimeout），某一路数据源挂了返回降级默认值，不拖垮整屏。</li>
    <li>JVM 侧显式配 <code>-Xms=-Xmx</code> 固定堆、用 G1、开 OOM 自动 dump，观察 GC 日志把 Full GC 频率压下来。</li>
  </ol>
<pre class="code" data-lang="java"><code>// 大屏首屏聚合：并行 + 超时 + 降级
public DashboardVO buildDashboard() {
    CompletableFuture&lt;LoadVO&gt; load = cf(() -> loadApi.current());
    CompletableFuture&lt;AlarmVO&gt; alarm = cf(() -> alarmApi.heatmap());
    CompletableFuture&lt;TreeVO&gt; tree = cf(() -> deviceApi.tree());
    try {
        CompletableFuture.allOf(load, alarm, tree).get(1, TimeUnit.SECONDS);
        return new DashboardVO(load.getNow(null), alarm.getNow(null), tree.getNow(null));
    } catch (TimeoutException e) {
        // 超时路用缓存里的上一次值兜底，先出屏再补
        return DashboardVO.fromCache();
    }
}</code></pre>
  <p><strong>效果与坑</strong>：首屏总耗时从约 700ms 降到约 300ms（取决于最慢一路），大屏打开即见。真实踩过的坑：</p>
  <ul>
    <li><span class="tag-pit">坑</span><strong>parallelStream 跑远程 IO</strong>：慢查询把公共 ForkJoinPool 占满，拖垮其他用 parallelStream 的业务——IO 密集任务要用自己声明的业务线程池，别共享公共池。</li>
    <li><span class="tag-pit">坑</span><strong>并行写同一聚合 Map 偶发丢数据</strong>：换成 <code>ConcurrentHashMap</code> + 不可变结果对象后消失。</li>
    <li><span class="tag-pit">坑</span><strong>Full GC 频繁</strong>：根因是每次聚合都 new 大列表又很快丢弃，Eden 被打爆频繁晋升；改用对象复用与批量查询减少短命分配后，Full GC 从几分钟一次降到几十分钟一次。</li>
  </ul>
