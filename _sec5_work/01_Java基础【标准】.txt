  <h2><span class="num">5</span>使用案例（真实项目落地）</h2>
  <h3>案例：DCP-RMP 需求管理平台——Service 层的集合/Stream/异常/IO 日常</h3>
  <p><strong>业务场景</strong>：DCP-RMP（需求管理平台，2026 年起，Spring Boot 3 + Java 17）后端要做需求列表的多条件筛选、按状态汇总、批量导出需求清单为文本文件等功能。这些都是典型的"从数据库查出 List，在内存里加工，再返回或落盘"的 Service 层活。</p>
  <p><strong>落地步骤</strong>：</p>
  <ol>
    <li>DAO 层用 MyBatis 查出 <code>List&lt;Requirement&gt;</code>，Service 不再手写嵌套 for 循环，统一用 Stream 做筛选、分组、映射。</li>
    <li>可能为空的查询结果一律返回 <code>Optional</code>，Controller 层用 <code>orElseThrow</code> 转成统一错误结构，杜绝 Service 里返回 null 导致前端拿到"莫名其妙的 200 空体"。</li>
    <li>导出功能写文本文件用 try-with-resources，保证文件句柄关闭，避免线上文件句柄泄漏。</li>
    <li>业务规则不满足时抛 <code>BizException</code>（继承 RuntimeException），由全局异常处理器统一转 JSON，不写 printStackTrace。</li>
  </ol>
<pre class="code" data-lang="java"><code>// Service：多条件筛选 + 分组汇总，一条流水线
public ReqSummaryVO summarize(List&lt;Requirement&gt; all, Set&lt;Long&gt; myTeamIds) {
    Map&lt;RequirementStatus, Long&gt; byStatus = all.stream()
        .filter(r -> myTeamIds.contains(r.getTeamId()))   // 只统计本团队
        .collect(Collectors.groupingBy(
            Requirement::getStatus, Collectors.counting()));
    long overdue = all.stream()
        .filter(r -> r.getDueDate().isBefore(LocalDate.now()))
        .filter(r -> r.getStatus() != RequirementStatus.CLOSED)
        .count();
    return new ReqSummaryVO(byStatus, overdue);
}

// 导出需求清单：try-with-resources 写文件
public void exportToFile(List&lt;Requirement&gt; rows, Path target) throws IOException {
    try (var writer = Files.newBufferedWriter(target, StandardOpenOption.CREATE)) {
        for (Requirement r : rows) {
            writer.write(r.getId() + "\t" + r.getTitle() + "\t" + r.getStatus() + "\n");
        }
    } // writer 自动关闭
}</code></pre>
  <p><strong>效果与坑</strong>：列表加工逻辑从"两层嵌套 for + 临时 HashMap"压缩成一条声明式流水线，code review 时一眼能读懂业务意图。真实踩过的坑：</p>
  <ul>
    <li><span class="tag-pit">坑</span><strong>toMap key 重复</strong>：<code>Collectors.toMap</code> 在 key 重复时直接抛 <code>IllegalStateException</code>，后来统一加 merge 函数 <code>(a, b) -> a</code> 兜底。</li>
    <li><span class="tag-pit">坑</span><strong>lambda 里抛受检异常编译不过</strong>：Stream 的 Consumer 签名不允许抛受检异常，正确做法是在 lambda 外 try-catch 或抛非受检的 <code>BizException</code>。</li>
    <li><span class="tag-pit">坑</span><strong>导出没关流</strong>：跑几天后服务器 <code>too many open files</code>，改成 try-with-resources 后文件句柄泄漏归零。</li>
  </ul>
