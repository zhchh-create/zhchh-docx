    <h2><span class="num">5</span>使用案例（真实项目落地）</h2>
    <div class="warn-box">本人简历项目（DCP-RMP、源启）后端均为 SpringBoot 单体，未实际拆分微服务。本案例为基于单体现状做的"向微服务演进"选型评估与学习实践，非已上线履历。</div>
    <h3>案例：DCP-RMP 从单体到微服务的拆分边界评估</h3>
    <p><strong>业务场景</strong>：DCP-RMP 是 Vue3+SpringBoot 单体，Monorepo 前端已拆出 web/drawio/工作流多应用；后端所有模块（需求、团队、工作流、AI 集成）还在一个进程里。评估未来若按前端应用边界拆后端，该怎么拆。</p>
    <p><strong>落地步骤（评估）</strong>：</p>
    <ol>
      <li><strong>先不动</strong>：当前单体内聚度高、团队规模小，引入 Nacos+Gateway+Feign 会显著抬高运维成本，判定"过早拆分"。</li>
      <li><strong>预留边界</strong>：代码上已按 Controller/Service/DAO 分层、模块分包清晰，为将来按业务域拆服务留好接缝。</li>
      <li><strong>学习验证</strong>：本地用 Nacos + 两个最简 SpringBoot 服务跑通"注册→Gateway 路由→Feign 互调"最小闭环，理解链路而非生产部署。</li>
    </ol>
    <p><strong>关键代码（学习 demo）</strong>：即 4.2 的 Gateway yaml 路由与 4.3 的 <code>@FeignClient</code>，本地起两个服务即可打通。</p>
    <p><strong>效果与坑</strong>：评估结论是"现阶段维持单体、保持模块化"，把微服务作为技术储备。学习中踩的坑：</p>
    <ul>
      <li><span class="tag-pit">坑</span><strong>SpringBoot 与 SpringCloud 版本不匹配</strong>：用 Boot3 配了 Boot2 时代的 Cloud 版本，启动直接报类找不到——先查版本兼容表。</li>
      <li><span class="tag-pit">坑</span><strong>Gateway 用了阻塞式 API</strong>：网关是 WebFlux 响应式，误写阻塞调用会报警告并拖垮吞吐。</li>
      <li><span class="tag-point">要点</span><strong>拆分边界按业务域而非技术层</strong>：按"需求域/团队域"拆，不要把 Controller 层、DAO 层各拆成一个服务。</li>
    </ul>
