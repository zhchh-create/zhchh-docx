HTTP 与跨域请求

标准 定位：前后端数据通道——HTTP 协议报文、同源策略、CORS 与代理方案

前端几乎所有数据都走 HTTP。本页讲清请求/响应报文结构、状态码、浏览器同源策略、CORS 预检机制，以及工程上最常用的跨域解法（开发态 Vite proxy、生产态网关）。案例取自 业务系统 的前后端联调与 Token 鉴权，以及 WebRTC 项目"信令走 HTTP、媒体走 UDP"的分层设计。

1技术点概览

是什么：HTTP（超文本传输协议）是客户端与服务端之间的"请求-响应"协议：浏览器发一个请求方法（GET/POST/PUT/DELETE）+ 路径 + 头 + 体，服务端回一个状态码 + 头 + 体。跨域则是浏览器的同源策略（Same-Origin Policy）带来的限制：页面源（协议+域名+端口）与接口源不一致时，默认禁止 JS 读取响应。CORS（跨源资源共享）是官方放行机制。

解决什么问题：同源策略本是安全防线（防止 A 站偷读 B 站的数据），但前后端分离后，前端跑在 localhost:5173、后端在 :8080，天生不同源，必须靠 CORS 或代理放行。理解这套机制，就知道"为什么 Postman 能调通、浏览器却报跨域"。

2核心概念

2.1 请求与响应报文结构（Message）

一句话定位：HTTP 报文 = 起始行 + 头 + 空行 + 体；Header 是元信息通道。

  • 请求四块：请求行（方法+路径+版本）、请求头（Host/Content-Type/Authorization/Cookie）、空行、请求体（POST/PUT 数据，GET 一般没有）。
  • 响应同理：状态行（状态码+短语）、响应头、空行、响应体。

要点鉴权令牌放 Authorization，跨域放行也靠响应头——Header 是这两件事的关键通道。

2.2 常见状态码（Status Code）

一句话定位：状态码按首位分五类，前端拦截器就是基于这套分类做分支。

  • 2xx 成功：200 OK、201 Created、204 无返回体。
  • 3xx 重定向：301 永久、302 临时、304 走缓存。
  • 4xx 客户端错：400 参数错、401 未认证、403 无权限、404 不存在。
  • 5xx 服务端错：500 内部错、502/504 网关/超时。

工程落点axios 拦截器按 401 跳登录、5xx 提示服务异常。

2.3 同源策略（Same-Origin Policy）

一句话定位：同源要求协议+域名+端口三者一致；跨域不是发不出去，而是浏览器不让 JS 读响应。

  • 拦截点在读不在发：不同源时请求真到了后端，但浏览器拦截 JS 读取响应。
  • 目的：防止恶意站偷读已登录站点的数据。
  • 例外：img/script/link 标签天然跨域加载资源，这也是 JSONP 的原理。

本质"跨域错误"= 你发得出去、读不回来。

2.4 CORS 与预检请求（Preflight）

一句话定位：CORS 是后端用响应头主动放行；非简单请求会先发 OPTIONS 预检。

  • 放行头：Access-Control-Allow-Origin 指明允许哪个源。
  • 读自定义响应头：跨域时 JS 默认只能读到少数简单响应头（Cache-Control、Content-Type 等），要读取自定义头（如分页 X-Total-Count），后端必须再回 Access-Control-Expose-Headers: X-Total-Count——否则前端 resp.headers.get() 拿到 null。
  • 简单请求：GET/POST 且只用安全头、Content-Type 仅 text/plain 等，直接发，浏览器看响应头放行。
  • 非简单请求：PUT/DELETE、自定义头（如 Authorization）、JSON body，先发 OPTIONS 预检，同意后才发真正请求。

坑带 Authorization 或 application/json 的接口几乎都是非简单请求——本地联调报跨域，先看 OPTIONS 预检有没有放行。

2.5 凭证与 Cookie（Credentials）

一句话定位：跨域默认不带 Cookie；要带得前后端同时配置，且 Allow-Origin 不能写 *。

  • 前端：fetch(...,{credentials:'include'}) 或 axios withCredentials:true。
  • 后端：CORS 头要 Access-Control-Allow-Credentials:true，且 Allow-Origin 必须是具体源、不能写 *。

实践业务系统 用 Bearer Token 放 Authorization 头，不依赖 Cookie，绕开了这层。

3工作原理与流程

3.1 一个带预检的跨域 POST 请求怎么走

图 2 非简单请求的 CORS 预检时序（示意）

  1. 预检：浏览器发现这是非简单请求（JSON body + 自定义头），先发 OPTIONS 探口风。
  2. 应答：后端在预检响应里回 Access-Control-Allow-Origin、Allow-Methods、Allow-Headers。
  3. 正式请求：预检通过，浏览器才发真正的 POST。
  4. 放行读取：正式响应带 CORS 头，JS 才能拿到数据。

4核心语法与 API 要点

4.1 fetch 带鉴权头

const res = await fetch('/api/requirements', {
  headers: {
    'Authorization': 'Bearer ' + getToken(),   // Token 放自定义头
    'Content-Type': 'application/json'          // 这个头会触发预检
  }
});
if (!res.ok) throw new Error('HTTP ' + res.status);
const data = await res.json();

4.2 Vite 开发代理（开发态最常用）

// vite.config.ts：把 /api 开头的请求转发到后端，浏览器看到的是同源
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,          // 改 Host 头为目标地址
      }
    }
  }
};

5实战项目经验（实战落地）

5.1 项目背景

一句话定位：业务系统 前后端分离跨域联调 + Token 鉴权；以及 WebRTC 信令走 HTTP、媒体走 UDP 的分层。

  • 业务系统：前端 Vite 跑 localhost:5173，后端 SpringBoot 在 :8080，跨域且需登录态。
  • WebRTC 播放器：建连协商（SDP/ICE）走 HTTP，音视频媒体走 SRTP/UDP。

5.2 我的角色与职责

  • 角色：前端开发，负责本地联调代理、鉴权拦截与请求封装。
  • 团队与分工：前端与后端 Java 团队联调，我定前端请求层，与后端对 CORS/Token 方案。

5.3 技术栈

  • Vue3 + Vite + axios + SpringBoot；生产 Nginx 反代；WebRTC（信令 HTTP/WS，媒体 UDP）。

5.4 落地设计

  • 开发态代理：Vite proxy 把 /api 代理到 :8080，浏览器侧同源。
  • 统一鉴权：axios 请求拦截器注入 Authorization: Bearer <token>，响应拦截器遇 401 跳登录。
  • 生产同源：Nginx 把前端静态与 /api 反代到同域名。

5.5 关键实现要点

// axios 请求拦截器：统一注入 Token
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = 'Bearer ' + token;
  return config;
});
// 响应拦截器：401 统一跳登录
api.interceptors.response.use(
  (res) => res.data,
  (err) => {
    if (err.response?.status === 401) location.href = '/login';
    return Promise.reject(err);
  }
);

5.6 真实问题与解法

  • 预检没放行：后端起初没配 CORS，OPTIONS 预检 404——请求根本没到业务接口；补 CORS 后正常。
  • credentials 与 * 冲突：曾用 credentials:include 配 Cookie，后端 CORS 写 * 被浏览器拒；改用 Bearer Token 头绕开。
  • 信令/媒体分层混淆：误以为媒体也走 HTTP，实际信令走 HTTP/WS、媒体走 SRTP/UDP，混了延迟和带宽都不对。

5.7 量化成果

  • 本地联调无跨域报错，鉴权全局统一，401 自动跳登录。

5.8 协作与排期过程

  • 契约先行：与后端约定 Token 放 Authorization 头、401 即跳登录。
  • 联调协商：预检 404 与 CORS * 冲突问题和后端一起定位，最终定 Bearer Token 方案。

5.9 复盘与可复用经验

  • 代理优于开 CORS：开发态用 Vite proxy 从源头避免跨域，省掉一堆 CORS 调试。
  • credentials 不能配 *：带 Cookie 的跨域，源必须显式列出。
  • 分清控制面/数据面：信令是控制面（HTTP/WS），媒体是数据面（UDP），选型别混。

5.10 面试讲法

实战要点用 Vite proxy + axios 拦截器统一解决 业务系统 跨域与 Token 鉴权，并讲清 WebRTC 信令走 HTTP、媒体走 UDP 的分层。

6易错点与面试重点

6.1 OPTIONS 预检失败被当成接口错误

一句话定位：非简单请求的 OPTIONS 预检被拒，真正请求根本没发出。

  • 现象：控制台跨域报错，但后端日志没看到请求。
  • 正解：看 Network 里 OPTIONS 的响应，配好后端 CORS 头。

6.2 带 Cookie 跨域不生效

一句话定位：withCredentials 三件套缺一不可，且 Allow-Origin 不能为 *。

  • 现象：设了 withCredentials，Cookie 还是没带上。
  • 原因：前端 withCredentials、后端 Allow-Credentials、Allow-Origin 不能为 *，三者缺一不可。
  • 正解：逐项核对；或干脆用 Bearer Token。

6.3 跨域错误被浏览器"吞掉"

一句话定位：跨域响应被拦截，JS 拿不到真实内容——先绕开浏览器验证后端。

  • 现象：报错信息笼统，看不到真实响应。
  • 正解：用 Postman/curl 直接打后端确认接口本身正常，再排查 CORS。

6.4 GET 误带 body、Content-Type 错

一句话定位：GET 用 query，POST 发 JSON 必须设 Content-Type。

  • 现象：GET 请求带了 JSON body，或 Content-Type 与实际不符。
  • 正解：GET 用 query；POST 发 JSON 记得设 Content-Type: application/json（否则后端收不到）。

6.5 304 与缓存误判

一句话定位：改了接口却拿到旧数据，多半是 GET 响应被缓存了。

  • 现象：改了接口但前端拿到旧数据。
  • 原因：浏览器/中间层缓存了 GET 响应。
  • 正解：响应头合理设置 Cache-Control，或对查询参数加时间戳。
