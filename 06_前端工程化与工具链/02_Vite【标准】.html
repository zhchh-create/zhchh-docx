Vite 构建工具

标准 定位：dev 用浏览器原生 ESM、build 用 Rollup——把冷启动从"打包完"变成"几乎为零"

Vite（法语"快"）是尤雨溪 2020 年推出的新一代构建工具。它 dev 模式不打包整棵依赖图，而是利用浏览器原生 ES Module 按需编译请求的模块；生产构建则交给成熟的 Rollup。本页讲清它的双模式架构、依赖预构建 optimizeDeps、proxy/别名配置，并用 业务系统（Vue3+TS+Vite+pnpm）的真实配置收尾，同时讲清它与 Webpack 的取舍。

1技术点概览

是什么：Vite 是面向现代浏览器的前端构建工具，由两部分组成：

  • dev server：基于原生 ESM，HMR、TS、JSX、CSS 预处理开箱即用。
  • 生产构建：基于 Rollup 的 vite build，打包优化成可部署静态资源。

与 Webpack 的根本区别在 dev 模式：Webpack 启动前要把整棵依赖图打包完才服务；Vite 利用浏览器已支持 <script type="module">，让浏览器直接请求各模块，服务器只在收到请求时即时转译那一个文件。

解决什么问题：中大型项目里 Webpack dev server 冷启动动辄几十秒到几分钟、改一行也要等重新构建。Vite 干掉了"启动要打包全部"：

  • 启动几乎瞬时，HMR 无论项目多大都保持亚秒级。
  • 现状：2023 年后新建 Vue/React 项目几乎都默认用 Vite——业务系统 正是选型它。

2核心概念

2.1 原生 ESM dev server

一句话定位：Vite dev 顺着浏览器原生 ESM 按需转译，不打包，所以项目再大启动也快。

  • 关键原理：浏览器原生 <script type="module"> 直接发请求加载 import 的模块。
  • 按需转译：import Foo from './Foo.vue' 原样交给浏览器，浏览器请求 /src/Foo.vue，服务器实时转译返回。
  • 为什么快：只有"被浏览器请求到的模块"才被转译，不整图打包。

2.2 依赖预构建（Dependency Pre-bundling / optimizeDeps）

一句话定位：用 esbuild 把 node_modules 第三方依赖预打成少数 ESM 文件，避免浏览器发几百个请求。

  • 问题：很多包内部是 CommonJS、拆成几百个小文件，逐个请求会发几百次 HTTP。
  • 做法：启动时用 esbuild（Go 写的，很快）把依赖预打成少数几个 ESM 文件——即 optimizeDeps。
  • 触发时机：只在依赖变化时重跑，日常业务改动不触发。

"Vite 快但不是完全零启动"——它仍预构建了依赖，只是不碰业务代码。

2.3 HMR（Hot Module Replacement，热更新）

一句话定位：基于原生 ESM，改一个模块只失效并重求它，保留页面状态。

  • 机制：改某模块时只通知浏览器该模块失效并重请求，保留其他模块与页面状态。
  • 为何轻量：不像 Webpack HMR 要注入大量 runtime，无论应用多大，更新一个模块的代价近似常数。
  • 组件级 HMR：Vue/React 官方插件在此之上做"改组件不刷新整页、保留状态"。

2.4 双模式：dev 用 ESM / build 用 Rollup

一句话定位：Vite dev 与 Vite build 是两套引擎——dev 快不等于 build 快。

  • dev：浏览器原生 ESM + 即时转译（不适合直接生产：几百请求、未压缩、旧浏览器兼容问题）。
  • build：交给 Rollup，做代码分割、tree-shaking、压缩、hash 命名——这才是上线产物。

build 阶段的优化目标与 Webpack 一致；"dev 快"不等于"build 也快"。

2.5 配置文件与环境变量

一句话定位：配置在 vite.config.ts；前端可读的环境变量必须 VITE_ 前缀。

  • 配置：vite.config.ts，比 Webpack 简洁很多。
  • 环境变量：走 .env 文件，前端能访问的必须以 VITE_ 开头（如 VITE_API_BASE）。
  • 读取：import.meta.env.VITE_API_BASE。

VITE_ 前缀是刻意的安全设计，防止把服务端密钥暴露给前端——写成无前缀的变量在前端取到 undefined。

3工作原理与流程

3.1 dev 请求处理：一次模块请求经历了什么

图 2 Vite dev 的按需编译流程（示意）

  1. 加载入口 HTML：Vite 把 /index.html 作为入口（注意：Vite 以 HTML 为入口，不像 Webpack 以 JS entry 为中心），里面的 <script type="module" src="/src/main.ts"> 直接生效。
  2. 浏览器按需发请求：解析 main.ts 时，浏览器看到 import App from './App.vue'，自己发请求去拿这个模块。
  3. Vite 即时转译：服务器收到 /src/App.vue，用 Vue 插件把 .vue 转成浏览器能跑的 ESM JS 返回。
  4. 依赖走预构建产物：import lodash from 'lodash' 这类被重写到 /node_modules/.vite/deps/lodash.js，命中之前预打包的文件，避免几百个小请求。

4核心语法与配置要点

4.1 一份 vite.config.ts（proxy + 别名 + 预构建）

import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import path from 'path';

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: { '@': path.resolve(__dirname, 'src') }   // 等价 Webpack 的 @ 别名
  },
  server: {
    port: 5173,
    proxy: {
      '/api': { target: 'http://localhost:8080', changeOrigin: true,
                rewrite: (p) => p.replace(/^\/api/, '') }
    }
  },
  optimizeDeps: {
    include: ['element-plus', 'axios']   // 显式声明预构建依赖，避免首次打开时按需才发现
  }
});

4.2 环境变量（VITE_ 前缀是硬规则）

# .env.development
VITE_API_BASE=/api
# .env.production
VITE_API_BASE=https://rmp.example.com
const base = import.meta.env.VITE_API_BASE;   // 读环境变量
// import.meta.env.MODE / .DEV / .PROD 是内置布尔量

4.3 路由懒加载（与 Webpack 写法一致）

// Vite 同样支持动态 import()，build 时 Rollup 自动分包
const routes = [
  { path: '/design', component: () => import('@/views/Design.vue') }
];
import.meta.glob：Vite 特有的批量动态导入——import.meta.glob('./views/**/*.vue') 可一次性按目录懒加载所有模块（路由自动注册常用）；要立即加载用 { eager: true }。生产侧想手动拆大库，则在 build.rollupOptions.output.manualChunks 里把 element-plus 等单独成 chunk。

5实战项目经验（实战落地）

5.1 项目背景：业务系统 多应用 Vite 工程

一句话定位：业务系统 是 pnpm monorepo，多个应用都用 Vite，要配好代理、别名、预构建并共享配置。

  • 项目：需求管理平台 业务系统（2026-，Vue3+TS+Vite+Pinia+ElementPlus）。
  • 结构：web 主应用 + drawio + 工作流多应用；公共包有 API 客户端/通用组件/表单设计器渲染器等。

5.2 我的角色与职责

  • 分工：我负责前端 Vite 配置、API 客户端与公共包；后端 SpringBoot 独立团队。前端组小团队协作。

5.3 技术栈

  • Vue3 + TS + Vite + Pinia + ElementPlus + pnpm workspace；OpenAPI 自动生成 TS 接口客户端。

5.4 落地设计：代理/别名/预构建/环境变量

  • 关键API 代理：dev 时 /api 代理到本地 SpringBoot，绕开跨域；生产由 Nginx 反代。
  • 别名：@→src，与 TS paths 同步。
  • 预构建：element-plus/axios 列入 optimizeDeps.include，避免首屏才触发预构建闪一下。
  • 环境变量：VITE_API_BASE 供 OpenAPI 客户端拼 baseURL。

5.5 关键实现要点

// API 客户端读环境变量（与 OpenAPI 生成器配合）
import axios from 'axios';
export const http = axios.create({ baseURL: import.meta.env.VITE_API_BASE });

5.6 真实问题与解法（含量化对比）

  • 坑环境变量忘加 VITE_ 前缀：取到 undefined——前缀是硬规则。
  • 坑新依赖没触发重新预构建：删 node_modules/.vite 或重启 dev 即恢复。
  • 坑alias 两边不同步：TS 配了 vite.config 漏配，运行时报找不到模块。
  • 坑monorepo 内部包被误预打包：源码包需 optimizeDeps.exclude 排除。
  • 前后对比（估算）：dev 冷启动从 Webpack 时代几十秒降到 1 秒内。

5.7 量化成果

  • dev 冷启动与 HMR 亚秒级；多应用配置可复用；OpenAPI 客户端按环境变量自动切 baseURL。

5.8 协作与排期过程

  • 契约先行：Swagger/OpenAPI 先定接口契约，自动生成 TS 客户端，前后端并行。
  • 联调协商点：dev 代理路径与后端接口前缀对齐。

5.9 复盘与可复用经验

  • 要点VITE_ 前缀 + alias 两边同步是 Vite 最常踩的两个坑。
  • 要点内部包 exclude 出预构建：monorepo 源码包别让 Vite 打包。

5.10 面试讲法（一句话抓手）

一句话抓手："在实践中 业务系统 这个 pnpm monorepo 多应用里用 Vite，配了 dev 代理、@别名与 TS paths 同步、optimizeDeps 预构建和 VITE_ 环境变量，把冷启动从 Webpack 的几十秒压到亚秒级。"

6易错点与面试重点

6.1 dev 快 ≠ build 快

一句话定位：dev 靠原生 ESM 按需（不适合生产），build 走 Rollup 完整打包。

  • 坑误区：以为 Vite 生产构建也像 dev 那样瞬时。
  • 正解：生产 build 走 Rollup 做完整打包优化，大项目 build 仍要等。

6.2 环境变量必须 VITE_ 前缀

一句话定位：Vite 只把 VITE_ 前缀的变量暴露给前端，其余防泄漏。

  • 坑现象：import.meta.env.XXX 是 undefined。
  • 正解：前端要用的变量一律 VITE_ 开头。

6.3 预构建缓存导致新依赖不生效

一句话定位：装了新包却报错，多半是 .vite 预构建缓存没更新。

  • 坑现象：装了新包，dev 报错或行为异常。
  • 正解：重启 dev server 或删 node_modules/.vite；把常用依赖列入 optimizeDeps.include。

6.4 CommonJS 依赖在 Vite dev 下的坑

一句话定位：原生 ESM 不能直接 require，老 CJS 包靠预构建转成 ESM。

个别包导出方式怪异会报错，需 optimizeDeps.include 强制预构建或换 ESM 版依赖。

6.5 选型：什么时候仍该用 Webpack

一句话定位：深度绑定 Webpack 生态的老项目继续用 Webpack，新项目默认 Vite。

  • 继续 Webpack：极老、深度绑定大量自定义 Webpack loader/plugin 的存量项目，迁移成本高。
  • 本项目分界：数据编排平台/低代码（老，Webpack），业务系统（新，Vite）。
