技术栈详解 · 04 实时通信

音视频基础与流媒体协议

标准 定位：从裸数据到一帧画面的分层——编码、封装、传输、加密各管一段

WebRTC 浏览器那端的"黑盒"背后，是一整套音视频技术栈：像素经 H.264 编码成码流、封进 RTP、用 SRTP 加密、经 UDP 在 ICE 选好的链路上传输，接收端再抖动缓冲、解码上屏。本页把这四层讲清，并以 WebRTC 无插件播放器项目里实际配置的 H.264/Opus 参数、SRTP/DTLS、ICE 流程为例，最后解释"延迟到底从哪来"。

1技术点概览

是什么：音视频技术栈是一套分层协议族——"压缩 + 打包 + 传输 + 加密"的组合，而非单一技术：

  • 关键编码层：H.264/H.265 视频、Opus/AAC 音频，把原始像素/采样压成码流。
  • 封装层：MP4/FLV 把音视频轨道混装成文件；RTP 把码流拆成适合实时传输的包。
  • 传输层：RTP/RTCP 在 UDP 上实时传包与反馈，或 HLS 基于 HTTP 传分片。
  • 安全层：WebRTC 用 DTLS 协商密钥、SRTP 加密媒体包。

解决什么问题：原始 1080p@30fps 不压缩每秒上百 MB、网络传不动；用 TCP 传实时流又因"一个丢包阻塞后面所有包"越等越卡。音视频栈同时解决这两件：

  • 压缩：编码器把数据压到可传输的码率。
  • 低延迟传输：面向 UDP 的实时协议保证延迟可控。
  • 同步组织：封装格式把音视频同步地组织起来。

2核心概念

2.1 视频编码：H.264 与 I/P/B 帧

一句话定位：视频编码的本质是时间与空间冗余压缩，H.264 把帧分三类、靠帧间预测省码率。

  • 关键I 帧（关键帧）：自包含、不依赖其他帧，可独立解码，体积最大。
  • P 帧（前向预测）：只存与前面帧的差值，体积小。
  • B 帧（双向预测）：参考前后帧。
  • GOP：两个 I 帧之间隔多少帧。

丢一个 P 帧会花屏直到下一个 I 帧——后续帧都依赖那个参考帧。这就是前端要能主动请求 PLI/FIR 让编码器立刻出 I 帧的原因。

2.2 音频编码：Opus 与采样

一句话定位：音频数据量由采样率/位深/声道决定，WebRTC 事实标准是 Opus。

  • 原始数据量：采样率（如 48kHz）× 位深 × 声道数。
  • Opus（WebRTC 默认）：6-510kbps 可调，融合 SILK（语音优化）+ CELT（音乐优化），抗丢包、低延迟好。
  • 对比：AAC 更偏点播/音乐消费。本项目监控流视频为主、音频为辅，Opus 参数配在 SDP 的 m=audio 行。

2.3 RTP 与 RTCP（实时传输与控制协议）

一句话定位：RTP 负责带序列号/时间戳的包传输，RTCP 是它的控制面，跑在 UDP 上。

  • RTP：把 H.264/Opus 切成带序列号与时间戳的包，在 UDP 上传——序列号查丢包乱序，时间戳做唇形同步。
  • RTCP：周期性互发报告，统计丢包率/抖动/往返时间，供拥塞控制与码率自适应。

为什么实时用 UDP 而非 TCP：TCP 丢包会重传并阻塞后续包（队头阻塞），实时场景宁可丢几帧也不能越等越卡；"丢了怎么办"交给上层（请求关键帧）。

2.4 封装格式：MP4/FLV vs RTP

一句话定位：编码解决"怎么压"，封装解决"怎么装"，两者正交。

  • MP4：点播文件容器，moov 元信息在头部或尾部。
  • FLV：为 HTTP-FLV 直播设计的流式容器。
  • 实时场景：不用文件容器，直接把编码后的 NALU 拆进 RTP 包（RFC 6184 规定 H.264 怎么拆），省掉整段封装等待——这正是 WebRTC 低延迟的一部分。

2.5 SRTP/DTLS 与 ICE（安全与打洞，承接前两页）

一句话定位：DTLS 协商密钥、SRTP 加密媒体、ICE 找路，三者共同构成"传输/加密层"。

  • DTLS：握手期协商密钥（详见 WebRTC 页 2.6）。
  • SRTP：用这把密钥加密后续 RTP 包。
  • ICE：NAT 后找一条能通的链路（host/srflx/relay 候选 + STUN 打洞）。

3工作原理与流程

3.1 端到端延迟到底从哪来

这是流媒体选型的核心问题。一路实时视频的总延迟，是下面几段的累加；理解每一段在哪、能不能压，是判断"为什么 HLS 慢而 WebRTC 快"的钥匙。

图 2 端到端延迟的构成（示意，数值为量级参考）

  1. 采集+编码：摄像头采样、编码器按帧出流，取决于帧率与 GOP 策略。
  2. 网络传输：包从源到服务器、再到浏览器的往返。走直连(srflx)低，走 TURN 中继(relay)高。
  3. 抖动缓冲（延迟最大且最可调的一段）：网络会抖动，接收端缓存若干包再按时间戳平滑播放。缓冲越大越抗抖，但延迟越大——这是"延迟 vs 流畅"的直接权衡，WebRTC 的 JitterBuffer 会动态调它。
  4. 解码与渲染：硬解码快，软解码慢且吃 CPU；渲染按显示器帧节奏上屏。
  5. HLS 的额外延迟：切片要凑满一个分片时长（常见 6 秒），还要经 CDN 缓存与播放器缓冲，这就是它做不了实时监控的根本原因。

4核心语法与配置要点

4.1 SDP 里和编码相关的关键行（读懂它）

m=video 9 UDP/TLS/RTP/SAVPF 96 97       ; 视频媒体行：端口/传输/负载类型
a=rtpmap:96 H264/90000                   ; pt=96 对应 H.264，90kHz 时钟
a=fmtp:96 profile-level-id=42e01f;packetization-mode=1
a=rtpmap:97 rtx/90000                    ; 重传负载（NACK）
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2                ; pt=111 对应 Opus，48kHz 双声道
a=fingerprint:sha-256 AB:CD:...           ; DTLS 证书指纹
a=setup:actpass                          ; 本端既可做 DTLS client 也可做 server

读懂 SDP 是排查"协商出了什么编码"的基本功：m= 行列出本端支持的 payload type，a=rtpmap 映射到具体编码与时钟，a=fmtp 给该编码的参数（H.264 的 profile-level-id=42e01f 是 Baseline/Constrained 类，兼容性最好）。

4.2 协商时限定编码（本例不常用，但面试会问）

// 用 setCodecPreferences 把 H.264 排到首选，避免协商出兼容性差的编码
var sender = pc.getSenders()[0];
var codecs = RTCRtpSender.getCapabilities('video').codecs;
var h264 = codecs.find(function (c) { return c.mimeType === 'video/H264'; });
if (h264) sender.setCodecPreferences([h264].concat(codecs));   // 实例方法：sender.setCodecPreferences(codecs)
// 注：纯接收场景由对端 offer 决定，这里主要用于本端需要约束编码的情况

4.3 编码器侧常见参数（服务端/源端，前端需理解）

# 以 ffmpeg 把 RTSP 转 WebRTC 喂 Janus 时的常见参数（理解用）
# -c:v libx264   用 H.264 软编码
# -profile:v baseline  选兼容性最好的 profile，老浏览器/硬解都支持
# -g 30           GOP=30：每 30 帧一个关键帧（1s@30fps），花屏恢复更快但码率略高
# -preset ultrafast  降低编码延迟（牺牲压缩率）
# -tune zerolatency  专为低延迟直播调优

5实战项目经验（实战落地）

5.1 项目背景：无插件播放器的编码/加密/连接落地

一句话定位：前端不直接做编码，但要和后端把"用什么编码、加密怎么配、连接怎么打"约定清楚，否则要么协商不出来、要么老机器解不动。

  • 业务场景：WebRTC 无插件播放器（2020-2022），变电站摄像头流在浏览器低延迟播放。
  • 关键约束：值班现场有内核较旧的机器，编码兼容性是硬指标。

5.2 我的角色与职责

  • 分工：后端/网关侧负责编码参数与加密开关；我负责前端 RTCPeerConnection 连接配置、SDP 协商结果验证、按现场网络调打洞策略。

5.3 技术栈

  • 编码：H.264 baseline + Opus；加密：DTLS-SRTP；传输：ICE（STUN/TURN）。

5.4 落地设计：编码参数与连接流程的关键取舍

  • 关键选 H.264 baseline：兼容现场老硬解机器；High profile 在老机器上解不动会花屏。
  • GOP 约 1 秒：丢参考帧后恢复快。
  • 加密：Janus 开 DTLS/SRTP，SDP 带 fingerprint，前端用默认加密模式（WebRTC 本就不允许明文）。
  • 打洞顺序：ICE→DTLS→SRTP；iceServers 配 STUN+TURN，不强制 relay，优先直连。

5.5 关键实现要点

// 前端只配连接与加密，编码由 SDP 协商结果决定
var pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com:3478', username: 'u', credential: 'p' }
  ]
  // 不传 iceTransportPolicy=relay：优先直连，失败再中继
});
// 拿到 Janus 的 offer 后打印协商出的实际编码，便于排查
pc.addEventListener('track', function () {
  var r = pc.getReceivers()[0];
  if (r && r.getParameters().codecs) console.log('协商编码:', r.getParameters().codecs[0].mimeType);
});

5.6 真实问题与解法（含量化对比）

  • 坑profile 与解码端能力不匹配：后端最初用 High profile，现场几台老机器解码失败花屏——统一降到 baseline 后解决。
  • 坑现场封 UDP：ICE 全部失败，补 TURN 后才通。
  • 坑GOP 设太长：5 秒一个 I 帧时丢参考帧要等很久才恢复花屏；前后对比：改成约 1 秒 GOP 后花屏自愈明显变快。

5.7 量化成果

  • 端到端延迟稳定约 300-500ms（估算）；老机器兼容播放；偶发花屏靠 PLI + 短 GOP 自愈。

5.8 协作与排期过程

  • 契约先行：与后端定编码 profile、GOP、加密开关、STUN/TURN 地址，再联调。
  • 联调协商点：老机器花屏时，一起比对协商出的 mimeType 与现场解码能力，定位到 profile。

5.9 复盘与可复用经验

  • 要点兼容性优先选 baseline：监控这类有老机器的场景，别盲目上 High profile。
  • 要点短 GOP + PLI：实时低延迟场景，缩短关键帧间隔是花屏自愈的关键旋钮。

5.10 面试讲法（一句话抓手）

一句话抓手："在实践中无插件播放器里和后端对齐了 H.264 baseline + 1 秒 GOP + DTLS-SRTP，解决了老机器 High profile 花屏，并用短 GOP 把丢帧后的花屏恢复时间从秒级压到亚秒级。"

6易错点与面试重点

6.1 编码与封装分不清

一句话定位：H.264 是编码（怎么压），MP4 是封装（怎么装），两者正交。

  • 坑误区：把 MP4 当成"一种视频编码"。
  • flv.js 在解什么：解的是 FLV 封装容器，把里面的 H.264 喂给 MSE，真正解码的是浏览器。

6.2 为什么实时传输用 UDP 不用 TCP

一句话定位：TCP 可靠但有队头阻塞，实时流宁可丢帧也不等重传。

  • 要点TCP 队头阻塞：丢一个包，后面所有包都要等它重传，实时流越堵越延迟。
  • UDP：不保证可靠，但把丢包恢复（请求关键帧、NACK）交给应用层——RTP 正跑在 UDP 上。

6.3 花屏 = 丢参考帧，不是"网络卡"

一句话定位：P/B 帧依赖参考帧，丢参考帧就绿条/马赛克，直到下一个 I 帧。

正解：主动发 PLI/FIR 让对端立刻出关键帧；同时控制 GOP 长度，缩短自愈等待。

6.4 HLS 为什么做不了实时

一句话定位：HLS 要先切满一个分片再下发，延迟=切片+缓存+缓冲累加。

  • 坑现象：用 HLS 做监控，永远慢现场好几秒。
  • 原因：先切完整分片（≥6s）再 HTTP 下发，经 CDN 缓存与播放器缓冲。
  • 正解：实时监控选 WebRTC（或 LL-HLS），HLS 留给回放与大规模分发。

6.5 JitterBuffer 越长越好吗

一句话定位：缓冲是"抗抖动"与"低延迟"的权衡，不是越长越好。

缓冲大→弱网不卡但延迟高；缓冲小→延迟低但一抖就卡/花屏。WebRTC 的 JitterBuffer 动态自适应，不要手动把它压死。
